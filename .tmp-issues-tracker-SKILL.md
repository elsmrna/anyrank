# Issues Tracker

A lightweight, dependency-free issue tracker that lives inside the repo as flat markdown files. One file per issue under `issues/` at the project root. No JSON state, no daemon, no third-party tracker — just files that git tracks like any other source.

## When to use this skill

Use this skill whenever the user wants to record something for later — features they've decided to defer, bugs they noticed in passing, design decisions they want to revisit, stubs left in code, follow-up work surfaced during a discussion. Also use it proactively: when the user says "let's not do that now" or "we'll come back to that," ask if they want it captured as an issue.

Don't use this skill for active work in progress — that's what task lists, branches, and code itself are for. Issues are for things that aren't being done right now and might otherwise be forgotten.

## Workflow

### Opening a new issue

First, locate the project root. Look for one of these markers in the current working directory or its ancestors: `.git/`, `package.json`, `Cargo.toml`, `pyproject.toml`, `Project.yml`, `go.mod`, `CLAUDE.md`. If you cannot identify the project root with confidence, ask the user where the root is rather than guessing.

Next, check whether `issues/` exists at the project root. If it doesn't, create both `issues/` and `issues/README.md` using the README template at the end of this file. This is a one-time setup; subsequent issues in the same project skip this step.

Then create the issue file at `issues/<name>.md`. Filenames are lowercase kebab-case, descriptive, no numeric prefixes — `live-google-places.md`, `flaky-snapshot-test-on-ipad.md`, `migration-from-v2-to-v3.md`. Use the issue template below.

The reason for no numeric prefixes: numbering issues requires a counter, which collides on concurrent branches. The filename is the readable identifier; git history provides the ordering. If you find yourself wanting uniqueness disambiguation, append a short distinguishing word, not a number — `live-places-search.md` and `live-places-photos.md`, not `places-1.md` and `places-2.md`.

### Listing or finding issues

Open and deferred issues live at the top level of `issues/`. Closed issues live in `issues/closed/`. Use `ls issues/` to see what's still actionable, `ls issues/closed/` for the history, and `grep -r <term> issues/` (recursive — covers both) when you're asking "did we ever consider X?". To filter by status within a directory, grep on the metadata line: `grep -l "^\*\*Status:\*\* open" issues/*.md` for open, swap `open` for `deferred` to see those. The metadata format is intentionally greppable.

### Closing an issue

Three steps, all in the same change:

1. Flip the `Status:` line from `open` to `closed`.
2. Add a `**Closed:**` line near the top pointing to the resolving commit, PR, or date — at minimum a one-sentence summary of how it was resolved.
3. Move the file from `issues/<name>.md` into `issues/closed/<name>.md`. Create `issues/closed/` first if it doesn't exist.

The move keeps a bare `ls issues/` focused on actionable work while preserving the closed file as institutional memory. If a future contributor wonders "did we ever consider X?", a recursive grep across `issues/` still finds it.

Don't delete closed issues unless the issue was created in error.

When closing an issue, also scan the codebase for path references to its previous location (`issues/<name>.md`) and update them to the new path (`issues/closed/<name>.md`). Code comments, READMEs, and other docs that linked to the open issue should follow it to its new home.

### Updating an issue

Edit in place. The `Status:` line is the canonical state. Free-form notes can grow over time as new context emerges; that's fine. If an issue's scope drifts significantly, prefer closing the original and opening a new one rather than rewriting history.

## Issue template

Every new issue starts from this template:

```markdown
# <one-line title summarizing the issue>

**Status:** open
**Priority:** high | medium | low
**Effort:** S (<1 day) | M (1–3 days) | L (3+ days)

## Context

Why this matters and how it came up. Keep it to one to three short paragraphs.
A reader picking up this issue cold should know enough from this section to
decide whether to take it on.

## Acceptance criteria

- Concrete, verifiable things that need to be true to consider this done.
- One bullet per criterion.
- These are the contract the issue ships against — be specific.

## Notes

Free-form thoughts, alternatives considered, links to related issues, anything
that would help the person who eventually picks this up. Skip if there's
nothing to say.
```

Three section heads, not more. If an issue needs more structure than this, what it actually needs is a spec — write the spec elsewhere and link to it from the issue's Notes section.

## README template

When you create the `issues/` directory for the first time in a project, also create `issues/README.md` with this content:

```markdown
# Issues

Flat-file issue tracker. Each markdown file is a single open question, feature, or piece of work that surfaced during product discussion or implementation but isn't done yet. Open issues live at the top level; closed issues move to `closed/` so a bare `ls issues/` only shows what's actionable. The closed files stay in the repo as institutional memory — `grep -r X issues/` still answers "did we ever consider X?".

## File format

Each issue uses this header structure:

​```
# <one-line title>

**Status:** open | deferred | closed
**Priority:** high | medium | low
**Effort:** S (<1 day) | M (1–3 days) | L (3+ days)
​```

Then three sections: **Context** (why this matters, how it came up), **Acceptance criteria** (what makes this done), and **Notes** (free-form). Keep each section tight — issues are not specs.

## File naming

Lowercase, kebab-case, descriptive. No numeric prefixes — git history is the ordering, not the filename.

## Status meanings

`open` — actionable now or soon. Lives at `issues/<name>.md`.
`deferred` — known and intentional, not in current scope. Lives at `issues/<name>.md`.
`closed` — done; the file remains for history. Lives at `issues/closed/<name>.md` with `Status: closed` and (ideally) a `**Closed:**` line near the top pointing to the resolving commit or PR.

When closing an issue, flip the `Status:` line to `closed`, add the `**Closed:**` pointer, and move the file into `closed/` in the same change.
```

Note the backtick escape pattern in the embedded fenced code — when writing this README to disk, replace the zero-width-space-prefixed triple-backtick markers with bare triple-backticks. (The escape exists only because this SKILL.md itself is a markdown file and cannot otherwise nest a code fence.)

## Conventions and why they exist

The format above is deliberately small. Each constraint exists for a reason, and the reasoning is worth holding onto so future variants don't drift in the wrong direction.

**Three sections, not five or seven.** The temptation when designing an issue format is to add fields — labels, assignees, milestones, comments. Each new field is a tiny cost at write time and an aggregate burden at read time, and most go unused. The Context / Acceptance criteria / Notes split covers ~90% of the value of a real issue tracker at a fraction of the cognitive overhead.

**Bold metadata lines instead of YAML frontmatter.** YAML hides metadata from `cat`, `less`, and any reader that doesn't know the convention. Bold prose lines are visible in raw output, in any markdown renderer, and they grep cleanly. The tradeoff is that they aren't machine-parseable as YAML, but issues aren't meant to be machine-parsed — humans read them and grep filters them.

**Closed issues stay in place — in `closed/`.** Deleting closed issues throws away the most valuable artifact of an issue tracker, which is the answer to "did we ever think about this?" Keep them. The `closed/` subdirectory keeps the top-level `ls` focused on actionable work without losing the history. Disk is cheap; institutional memory is not.

**No issue IDs, no numbered filenames.** Numeric IDs require a counter, and counters collide on branches. The filename is the readable identifier. When referring to an issue in a commit message or another document, link to the file path: `issues/live-tmdb.md` for open issues or `issues/closed/google-oauth-sheets-sync.md` for closed ones, not `#42`.

## When to proactively offer

When the user says any of "let's defer that," "we'll come back to it," "out of scope," "TODO," "good idea but not now," or describes work that's been stubbed in code (a placeholder mock, a `notImplemented` throw, a TODO comment), surface the option to open an issue. Phrase it as a question, never a demand: "Want me to open an issue so we don't lose it?" The user can say no and the moment passes.

Also offer to capture issues at the end of a planning or design discussion when concrete decisions were made about what's in scope vs. what's deferred. The boundaries of "this milestone" are exactly the issues worth opening for "next milestone."

## What this skill explicitly doesn't do

This skill doesn't track assignees, milestones, sprints, or labels. If a project genuinely needs those, it has outgrown flat-file issues and should move to a real tracker.

It doesn't enforce schemas at write time — there's no linter checking that every issue has all three sections. The format is a convention, not a constraint. Issues that violate the format aren't wrong, just less consistent.

It doesn't sync with anything. If the user later wants to import these issues into GitHub Issues or Linear, that's a one-time scripted migration, not an ongoing sync.
