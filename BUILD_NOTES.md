# Build Notes — v1 Implementation

This document records what was built in the first implementation pass against `Spec.md`, what is intentionally stubbed, and what to do next. Read alongside `README.md`.

## What's in the box

The repo now contains 47 source and config files implementing the spine of the app: ~3,200 lines of Swift across the iOS app target, the unit test target, and the snapshot test target. The Xcode project itself is generated by xcodegen from `Project.yml`, not committed.

The data model is implemented as five SwiftData entities — `RankList`, `RankItem`, `ComparisonRecord`, plus `Category` and `Bucket` enums — under `AnyRank/Models/`. Lists own items and comparisons via cascade-delete relationships; metadata is stored as optional fields per category, with custom-category lists carrying a user-defined `customFieldNames` array and items carrying a parallel `customFieldValues` dictionary.

The ranking algorithm is split into three pieces under `AnyRank/Algorithm/`. `RankingSession` is a pure, observable state machine: bucket pick → bucket-constrained binary search → boundary check → optional tie-break → finished. Randomness is injected so tests are deterministic. `ScoreInterpolation` is a pure function for the linear within-bucket score formula. `RankingApplier` is the SwiftData side: it inserts items, renormalizes the affected bucket(s), persists comparison records, and bumps the periodic re-rank counter. The session never touches storage; the applier never decides positions.

The four core screens are all wired up. `ListsHomeView` shows lists grouped by category with empty-state copy. `ListDetailView` shows score-sorted items with bucket color accents, hides scores until a bucket has 3+ items, surfaces the periodic re-rank prompt banner, and supports swipe-to-delete with renormalization. `ItemDetailView` shows full metadata with category-specific sections, supports inline edits to name/notes/date/custom fields, and exposes "Re-rank" and "Delete" actions. `CreateListView` handles category pick + name + custom-field definition in a single form.

The add-item flow is the largest single screen group. `AddItemCoordinator` is the four-phase state machine (identifying → bucketPick → comparing → finished). `AddItemFlow` is the sheet that dispatches to category-specific search screens (`PlaceSearchScreen`, `MovieSearchScreen`, `CustomItemFormScreen`), then to `BucketPickerScreen`, then `ComparisonScreen`, then `AddItemResultScreen`. `RerankFlow` reuses the bucket-picker and comparison screens but skips the identification phase and applies the placement with `ComparisonKind.rerank` so the audit log distinguishes initial placement from later re-rank.

External services are abstracted behind `PlacesSearchService`, `MovieSearchService`, and `BookSearchService` protocols injected via SwiftUI environment. Mock implementations ship with a small canned dataset of LA-area restaurants, NY-area bars, recognizable movies, and canonical books — enough to exercise the search UIs offline. `AnyRankApp` picks the Live implementation for each service when its credentials are configured in `Secrets.xcconfig` (Places API key, TMDB read token, StoryGraph is still a stub), otherwise falls back to the mock. See the dedicated Places and Movies sections below.

`PreviewSupport` provides five seeded in-memory `ModelContainer` factories: empty, single-item, small-restaurants, full-restaurants-spanning-all-buckets, and multiple-lists-across-categories. Every view file has at least one `#Preview` block and major views have several.

## Auth layer (added after first pass)

Google OAuth sign-in is wired up under `AnyRank/Auth/`. Architecture: `AuthDriver` is a protocol, `GoogleAuthDriver` wraps `GoogleSignIn-iOS`, `MockAuthDriver` is the test/preview substitute. `AuthSession` is the `@Observable` class views actually consume — it holds the current `SignedInUser?`, exposes `signIn()` / `signOut()` / `attemptSilentRestore()`, and surfaces sign-in errors so the UI can render them. Tokens never escape the SDK's Keychain storage; `AuthSession` only carries the bits it displays.

Sign-in is exposed in two places. `SignInOnboardingView` is a first-launch sheet (gated by the `hasCompletedOnboarding` `@AppStorage` flag) that offers "Sign in with Google" alongside a prominent "Continue without an account" bypass — local-only mode is fully preserved. `SettingsView` is reachable from a gear icon on `ListsHomeView` and shows the same affordance for users who skipped initially, plus a sign-out action.

OAuth scopes at sign-in are `profile` and `email` only, deliberately. Sheets and Drive scopes are added later when the user enables sync in Settings (see [#5](https://github.com/elsmrna/anyrank/issues/5)), which re-prompts the consent screen — a known and intentional cost in exchange for a less-scary initial prompt.

The build degrades cleanly when no OAuth client ID is configured. `Secrets.swift` reads from Info.plist (populated via `Secrets.xcconfig` → `Project.yml` `baseConfiguration`); if the value is missing, `AnyRankApp` constructs a `MockAuthDriver` and the rest of the app behaves normally. Sign-in attempts surface a clear "not configured" error instead of crashing.

## Storage and Sheets sync (added after auth)

Storage moved from a SwiftData-backed model container to a hand-rolled `Repository` + `ListStorage` pair under `AnyRank/Storage/`. The on-disk layout is one CSV file per list (`<uuid>.csv` for items, `<uuid>_comparisons.csv` for the audit log) plus a top-level `index.json` carrying per-list metadata that doesn't fit in a CSV (category, custom field names, re-rank threshold). Files live under `<Application Support>/AnyRank/lists/`. `MemoryListStorage` is the in-process variant used by previews and snapshot tests. The CSV implementation in `CSV.swift` is intentionally small — it handles the dialect the app produces and what Google Sheets emits on its `values` API, which is enough; full Excel-style CSV is out of scope.

Sync is implemented under `AnyRank/Sync/`. `GoogleSheetsClient` is a thin HTTP wrapper over the Sheets v4 and Drive v3 APIs — create or find a spreadsheet, list tabs, read tab as CSV, upsert a tab from CSV, delete a tab. `SyncCoordinator` implements `SyncObserver` so the repository can call into it after persistence completes. The coordinator tracks status (`.disabled` / `.ready(spreadsheetID, lastSyncedAt)` / `.syncing` / `.error`) which the Settings view surfaces. Per-list pushes are debounced 2 seconds so rapid edits coalesce. After every flush, `SyncCoordinator` rewrites the `_index` tab (encoded by `SheetsIndexCodec`) which mirrors the local `index.json` and carries the metadata a pulled list needs to come back with the right category and custom field names. Without `_index`, pulled lists fall back to Custom — documented behavior for hand-created spreadsheets.

Sync is opt-in via a toggle in `SettingsView`. Turning it on requests the `drive.file` and `spreadsheets` OAuth scopes on top of the v1 profile+email — a deliberate split so the v1 consent prompt stays minimal. Turning it on runs `SyncCoordinator.connectSpreadsheet`. The spreadsheet ID is saved in `UserDefaults` keyed by the user's email, and that doesn't survive deleting the app. So when no ID is saved, it first looks in Drive for an existing "AnyRank Data" spreadsheet (`GoogleSheetsClient.findSpreadsheets`; the `drive.file` scope only shows files this app created) and creates one only if there isn't one. If it finds several, it prefers the newest one whose `_index` lists something. When it adopts an existing sheet, it brings back any lists the sheet has that the device doesn't, so a reinstall restores everything and a device that already made a few lists keeps them alongside the restored ones. Then it schedules a push for every list the device had.

The sync model is **local-primary, Sheet-as-backup, one-way push**. Local CSVs under Application Support are always the source of truth at read time — list rendering reads from the local store, never from the Sheet. Writes push to the Sheet via the debounced path (2 seconds of inactivity coalesces rapid edits) and a force-flush on scene `.background` via `SyncCoordinator.flushNow()` (wired in `AnyRankApp` via `@Environment(\.scenePhase)`). Pull only fires when the local store is empty (`pullChanges` is gated on `repository.lists.isEmpty`); that's the recovery path when a saved spreadsheet ID survives but the lists don't (for example, after restoring an iOS backup). Reinstalls go through `connectSpreadsheet` instead, since they lose the ID too. Outside that one case, the Sheet is purely a write destination — concurrent direct edits in the spreadsheet will be overwritten on the next push and are not supported.

The unit test target covers the algorithm: empty bucket, single-item bucket placed at top, single-item bucket placed at bottom with downward boundary check, demote on boundary, multi-item exact binary search, no-boundary-check at the lowest bucket, comparison-cap tie-break, score interpolation correctness, and decreasing-score invariants. The snapshot test target has reference points for `ListsHomeView` (empty, multiple lists), `ListDetailView` (full, single-item, empty), `ItemDetailView` (loved with score, single-item without score), `BucketPickerScreen`, `ComparisonScreen`, and `AddItemResultScreen`.

## Places integration (Restaurants, Bars, Custom-with-Maps)

The Google Places SDK is a Swift Package dependency declared in `Project.yml`. `GooglePlacesBootstrap.configure()` runs once at app launch and provisions `GMSPlacesClient` with the key from `Secrets.googlePlacesAPIKey` (Info.plist, populated from `Secrets.xcconfig` at build time). When the key is present `AnyRankApp` injects `LivePlacesSearchService` into the environment; when it isn't, it injects `MockPlacesSearchService` so the app stays usable for dev/preview/test.

`LivePlacesSearchService` does the standard two-stage flow — `findAutocompletePredictions` for the typeahead pass, then `fetchPlace` for each picked prediction — sharing one `GMSAutocompleteSessionToken` across both so Google bills the session as one rather than per-keystroke. Detail fetches run sequentially (cap of 8) to keep the implementation Sendable-clean under Swift 6 strict concurrency.

`PlaceSearchScreen` layers a sign-in gate on top: if the user isn't signed in, the screen replaces the search field with a "Sign in to look up places" prompt that triggers `AuthSession.signIn()`. Under the hood Places is API-key gated, not OAuth-gated — the sign-in requirement is a UX choice, positioning Maps integration as a perk of signing in.

Custom lists pick up the same flow via the new `RankList.linksToMapsLocation` flag (set by a toggle in `CreateListView`). When on, `ItemSearchScreen` dispatches Custom adds to `PlaceSearchScreen` with kind `.any` and stages items as `.custom`. Items carry the Maps metadata (placeID, address, lat/lng, Maps URL) regardless of their list's category, so the existing CSV codec round-trips them without changes. The flag itself round-trips through `index.json` and the Sheets `_index` tab.

## Maps (place lists)

Restaurants, Bars, and Maps-linked Custom lists (`RankList.isPlaceList`) get a round map button beside "Add" on list detail that swaps the ranked list for `ListMapView`. The map is an `MKMapView` wrapper (`RankedMapView`), because SwiftUI's `Map` can't cluster annotations or order them. Pins are bucket-colored with the item's rank, higher ranks draw on top (`MapFraming.zPriority`), and they cluster when zoomed out; tapping a cluster zooms into it. `MapFraming.initialRegion` centers on the user with 5 miles in each direction when any item is within 5 miles, and otherwise fits every item. `LocationProvider` asks for location the first time a map opens. The "Show my location on maps" setting turns it off, and when iOS access is denied the map shows a banner each time it opens. Items without coordinates stay off the map behind a "Find" pill, which uses `PlaceBackfill` to look each one up on Google Places and keep only an exact name match. See [#27](https://github.com/elsmrna/anyrank/issues/27).

## Movies integration (TMDB)

`LiveMovieSearchService` calls `GET /3/search/movie?query=…` on TMDB v3 with a Bearer read token, then fans out `GET /3/movie/{id}/external_ids` on the top hits to attach IMDB links. Poster URLs come from TMDB's `image.tmdb.org/t/p/w342` CDN. Detail fan-out is capped at 8 results and runs sequentially to stay Sendable-clean and rate-friendly. `Secrets.tmdbReadToken` reads from Info.plist (populated via `TMDB_READ_TOKEN` xcconfig at build time); `LiveMovieSearchService.init?()` returns nil when the token is missing, and `AnyRankApp` uses that signal to hand out `MockMovieSearchService` instead. No sign-in gate on Movies — TMDB is unaffiliated with Google, so tying it to sign-in would be misleading.

## Books integration (Open Library + StoryGraph URLs)

`LiveBookSearchService` hits Open Library's `/search.json` (keyless, generous rate limits) and maps each hit into a `BookSearchResult`. First-author-first-ISBN heuristic. StoryGraph URLs are constructed slug-optimistically from the title with a browse-URL fallback when the slug would be empty. Cover URLs come from `covers.openlibrary.org`. All artwork loads through `ArtworkCache` (used by `ArtworkView`), which keeps downscaled thumbnails in Caches and retries transient failures. It resolves Open Library cover-by-ISBN URLs, which StoryGraph and Goodreads imports produce, to cover-ID URLs via search: the ISBN endpoint allows only 100 requests per 5 minutes and answers "no cover" with a 1×1 GIF, which used to leave blank tiles in big imported libraries. `BookSearchResult.coverURL` and `RankItem.coverURLString` round-trip through the CSV codec's new `cover_url` column. See [#11](https://github.com/elsmrna/anyrank/issues/11).

## What's stubbed

Every category-specific search service is live:
- Restaurants / Bars / Stays → Google Places SDK, with Stays filtered to the `lodging` type ([#10](https://github.com/elsmrna/anyrank/issues/10), [#31](https://github.com/elsmrna/anyrank/issues/31))
- Movies → TMDB v3 REST + `/external_ids` for IMDB ([#12](https://github.com/elsmrna/anyrank/issues/12))
- Books → Open Library `/search.json` + optimistic StoryGraph slug ([#11](https://github.com/elsmrna/anyrank/issues/11))
- Anime / Manga → AniList GraphQL; `LiveAniListSearchService` serves both, varying only the media type ([#2](https://github.com/elsmrna/anyrank/issues/2), [#32](https://github.com/elsmrna/anyrank/issues/32))
- Video Games → IGDB via Twitch client credentials ([#3](https://github.com/elsmrna/anyrank/issues/3))
- Music (Albums + Songs) → Spotify Web API via client credentials ([#13](https://github.com/elsmrna/anyrank/issues/13))

The IGDB and Spotify services share `AppOAuthTokenStore` — a small actor that caches app-level OAuth 2.0 client-credentials tokens and refreshes on demand. Both are gated by their respective `<Provider>_CLIENT_ID` / `<Provider>_CLIENT_SECRET` in `Secrets.xcconfig`; either missing → the mock service is injected instead, so the app stays runnable without secrets.

The remaining stubs: Google Places photos on comparison cards (would need an extra Places SDK call per result — deferred; see [#16](https://github.com/elsmrna/anyrank/issues/16)) and the educational onboarding walkthrough.

## Imports and ranking sprees

A one-time import pulls a whole collection (Steam library, Letterboxd / Goodreads / StoryGraph CSV export, or a pasted list) into a list as a **queue**, then the user ranks it through the normal comparison flow at their own pace. Code lives in `AnyRank/Import/` (sources, `ImportMatcher`, `ImportStore`, `ImportEnricher`) and `AnyRank/Views/Import/` (`ImportFlowView`, `RankingSpreeView`, `ImportProgressCard`).

The queue (`ImportSession`) is persisted to `<Application Support>/AnyRank/imports.json`, local-only and not synced — only ranked items become part of the list (and therefore the Sheet). At most one session per list; importing more into a list with one running appends to its queue. Source ratings are carried as a *suggested* bucket on the bucket picker, never applied automatically. Queued items without artwork are enriched just in time from the category's search service, accepting exact normalized-title matches only. Sources: Steam (sign-in via Steam OpenID in a system web-auth sheet, or a profile link), Letterboxd (whole export .zip, read by the small `ZipReader`, or any CSV), IMDb (exact TMDB `/find` by IMDb ID), Goodreads, StoryGraph, and a pasted list. `FileImporters.detect` recognizes an export by its headers, so picking the "wrong" source still works. Steam reads libraries with one developer key, `STEAM_WEB_API_KEY` in `Secrets.xcconfig` — users never need one; without it the import runs against a sample library (and says so). Steam only shares libraries whose Game details are Public. See [#8](https://github.com/elsmrna/anyrank/issues/8).

## Visual design

The UI is themed from a single set of tokens in `AnyRank/Design/Theme.swift` (colors, bucket colors/glyphs, category tints, serif display type, motion) and shared components in `AnyRank/Design/Components.swift` (cards, primary/secondary/pressable button styles, artwork thumbnails, score badges, bucket distribution bar, search field). The palette is earthy: terracotta accent, stone, taupe, espresso ink, olive; dark mode is a deep espresso with lifted versions of the same hues. Every bucket carries a glyph as well as a color so buckets stay distinguishable without color vision. Views should reach for `Theme.*` rather than system colors.

The add-item and re-rank sheets share `PlacementFlowView`: each step is a real `NavigationStack` push driven by `AddItemCoordinator.path`, so back and edge-swipe step the state machine back. All category searches share `CatalogSearchScreen`, which debounces through `.task(id:)` (a new keystroke cancels the in-flight request) and keeps results on screen while the next query loads.

App icon, accent color, and launch background live in `AnyRank/Assets.xcassets`. The icon ("Head to head": two cards, the front one checked) is drawn by `swift scripts/app-icon.swift`, which writes the light, dark, and tinted PNGs. Edit the palettes or `artworkScale` there and rerun it rather than editing the PNGs. For eyeballing the UI with data, launch a Debug build with the `-seedDemoData` argument — an empty store gets filled with the preview datasets (see `Preview/DemoSeed.swift`).

Onboarding is not implemented — first launch drops the user into the empty-state of `ListsHomeView`, which has a primary "Create your first list" button. That's adequate for v1; full onboarding can come later.

Export and restore live in Settings → Your data (`ListArchive`, `ZipWriter`). An export is a .zip of the on-disk format, `index.json` plus each list's CSVs, written by a `FileListStorage` pointed at a staging folder. Restore reads the zip with `ZipReader`, loads it the same way, and swaps it in with `Repository.replaceLists(_:notifySync: true)`, so a Sheet follows along when sync is on. Import queues aren't included. See [#17](https://github.com/elsmrna/anyrank/issues/17).

## What might trip you up

Strict concurrency is enabled in `Project.yml`. SwiftData models bridge across actors with some friction; `RankingApplier` and `ScoreInterpolation.renormalize` are explicitly `@MainActor` so model mutations stay on the main actor. If you add new code that mutates model objects, mark it `@MainActor` too or you'll get warnings.

Snapshot tests rely on a pinned simulator (`iPhone 16 Pro`) — the precise simulator chosen affects the rendered images. The first test run writes reference PNGs under `__Snapshots__/`. Commit those PNGs as part of the same change that introduces a snapshotted view.

The `Project.yml` uses a Swift package dependency on `swift-snapshot-testing`. If `xcodegen generate` doesn't resolve packages automatically, open the generated project once and let Xcode resolve dependencies, then run tests.

The four buckets in the bucket picker are big tap targets but the visual treatment is deliberately neutral — color-coded outlines on tinted backgrounds. Spec § 8 called out the comparison screen and bucket picker as worth a dedicated design pass; the comparison screen shipped its pass (vertical stack, thumbnails, secondary text, step estimate — see [#4](https://github.com/elsmrna/anyrank/issues/4)). The bucket picker is next.

## Suggested first run

After `xcodegen generate`, open the project, pick the AnyRank scheme and an iPhone 16 Pro simulator, hit Cmd-R. The empty-state shows. Tap "Create your first list," pick Restaurants, name it, save. Tap "+", search for any restaurant, tap a result, pick a bucket, walk through whatever comparisons get presented. The result screen confirms the placement; tap Done. The new item appears in the list with its bucket color and (once the bucket has ≥3 items) a numeric score.

After getting the basic flow working, run Cmd-U to verify the unit tests pass. The snapshot tests will fail on the first run because they have no reference images yet — running them once writes the references; commit those PNGs and subsequent runs will assert against them.
